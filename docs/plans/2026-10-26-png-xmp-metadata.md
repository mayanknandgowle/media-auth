# Phase 2: bounded recorded static PNG XMP

## Objective, scope and acceptance

Expose recorded CreatorTool/CreateDate/ModifyDate/MetadataDate from one uncompressed static PNG iTXt XMP packet in CLI/extension, separately from EXIF. Preserve raw dates, encoded dimensions, four evidence states and conservative conclusions. Leave this increment uncommitted for review.

Accept one exact case-sensitive XML:com.adobe.xmp keyword in iTXt, compression flag 0, empty language/translated keyword and the existing limited UTF-8 XML/RDF subset. Ignore the compression-method byte for uncompressed text as required by PNG decoder rules. Search before/after contiguous IDAT through terminal IEND; CRC-check all chunks and retain the exact selected bytes used in CRC validation without rereading metadata. Duplicate selected packets, compressed XMP, legacy tEXt/zTXt XMP, unsupported headers/XML, animation, framing/CRC failures or later failures are INCONCLUSIVE without partial fields. Missing recognized keyword in the declared text-carrier scope is NOT_DETECTED; wrong MIME/missing ranges/I/O UNAVAILABLE; resource/cancel failures propagate. Unknown text values are neither extracted nor inflated.

Non-goals: decompression of metadata or pixels, general PNG/XML/RDF/XMP conformance, animation, new fields, other carriers, normalization/reconciliation, authenticity/provenance/detection, new dependencies/permissions/acquisition/storage or publishing this increment.

## Dependencies, risks and decisions

No new dependencies/permissions. Compressed XMP is deliberately deferred until bounded output/ratio/work/cancellation behavior can be shared across runtimes; identifying it never establishes absence. The strict uncompressed header/limited XML subset can reject valid unsupported metadata. Recorded claims can be forged/sensitive; no authenticated history. Cooperative limits are not a process sandbox or peak-memory guarantee.

Primary references inspected 2026-10-26: [W3C PNG third edition, text keywords/iTXt](https://www.w3.org/TR/png-3/#11iTXt) recommends the exact keyword, uncompressed flag and empty language/translation for XMP; uncompressed decoders ignore the method byte. [Adobe PNG support header](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/XMPFiles/source/FormatSupport/PNG_Support.hpp) confirms the canonical 22-byte header. Duplicate rejection and allocation caps are project policies. No external source code/media is copied.
