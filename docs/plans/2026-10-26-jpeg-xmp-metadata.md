# Phase 2: bounded recorded JPEG XMP

## Objective and acceptance

Add selected recorded XMP CreatorTool/CreateDate/ModifyDate/MetadataDate claims to CLI and extension inspection of JPEG. Keep fields separate from EXIF, unverified dates unchanged and conclusions conservative. Leave this increment uncommitted for review.

Accept one standard XMP APP1 identifier before the first SOS/EOI and a deliberately limited UTF-8 XML/RDF subset. Resolve field names by namespace URI, not prefix spelling. Support direct scalar properties and Description attributes, optional xmpmeta and packet wrappers, and predefined/numeric XML references without recursive expansion. Unknown bounded properties are not extracted. Require an empty rdf:about; reject ambiguous duplicate selected fields, DTD/entity declarations, external resources on selected fields, unsupported XML constructs, non-UTF-8 data and extended XMP rather than silently producing partial fields. No standard packet in the declared pre-scan scope is NOT_DETECTED, unsupported/malformed/ambiguous data INCONCLUSIVE, absent byte access/wrong MIME/I/O UNAVAILABLE; resource/cancel errors propagate.

Non-goals: general XML/RDF/XMP conformance, XML comments/CDATA/arbitrary processing instructions, extended packet reassembly, other XMP carriers, RDF arrays/qualifiers for selected scalar fields, author/GPS/title/history extraction, normalization/reconciliation, authenticity, new dependencies/permissions/acquisition/storage, or publication of this increment.

## Architecture/boundaries

Reuse the existing bounded metadata range reader under a neutral name, preserving EXIF behavior, and extract the shared JPEG pre-scan segment walk for both EXIF/XMP. Add `media-auth.jpeg-xmp` v0.1.0 to the explicit registry (eleven providers). Keep core/probes/fusion untouched. The XMP adapter owns UTF-8 decoding via the standard TextDecoder available in supported Node/Chromium runtimes; the limited XML/RDF reader uses no DOM, network or filesystem. No dependency is introduced. Record field values and packet presence as XMP observations with unassessed confidence; do not run EXIF dimension comparison on them.

Bound a standard packet by its JPEG segment (at most 65,504 XML bytes), requests at min(4096,maxChunkBytes), input/segment/work limits, XML depth 8, nodes 128, attributes 16 per element, namespace bindings 32, attribute values 2048 and selected field strings 256 UTF-16 units. Markers/fill/XML tags/attributes/text consume shared maxChunks; retain no output after any later failure in the scoped carrier or packet. Entity replacement is single-pass and never resolves URLs. Claims never control pixel allocation. Add source-specific text UI fields and JSON exports, documentation and ADR 0014.

## Dependencies/risks/decisions

No dependency or permission change. The XML reader is intentionally a small rejecting subset, not a general-purpose standards parser; unsupported valid documents are inconclusive. Reject rather than guess at RDF qualifiers/subjects or extended packets. UTF-8/JSON/text rendering do not verify the truth of recorded claims. Cancellation remains cooperative; limits are not a process sandbox or peak-memory guarantee.

Primary references: [Adobe XMP specifications](https://developer.adobe.com/xmp/docs/xmp-specifications/) (Parts 1 and 3), [XMP Basic namespace](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp/) and W3C XML namespace/character rules. No third-party source, specification text or external media is redistributed.
